A maioria das linguagens modernas não vive em uma “caixa pura”. Elas combinam recursos para resolver problemas reais.

Programação não estruturada

Nos primeiros estilos imperativos, o controle podia saltar livremente entre trechos do programa. A metáfora é um mapa de cidade sem placas: dá para chegar, mas é difícil explicar o caminho.

Força

Próxima da máquina; flexível; útil em baixo nível.

Problema

Fluxo difícil de seguir; manutenção e prova de correção ficam frágeis.

$i = 0;
inicio:
if ($i >= count($pedidos)) goto fim;
processar($pedidos[$i]);
$i++;
goto inicio;
fim:
echo "Concluído";

O problema não é um salto isolado. É a perda de estrutura quando saltos viram a arquitetura do raciocínio.

Dijkstra, “Go To Statement Considered Harmful”, Communications of the ACM, 1968.

Funções e procedimentos

Procedimento

Bloco nomeado que executa uma ação. Pode alterar estado, imprimir, salvar ou enviar.

function enviarEmail($pedido): void {
    // ação com efeito colateral
}

Função

Idealmente recebe entradas e produz uma saída. Em matemática, função enfatiza transformação.

function total(array $itens): float {
    return array_sum($itens);
}

Nomear uma operação é o primeiro passo para transformar código em vocabulário.

Van Roy & Haridi (2004); fundamentos de decomposição e abstração procedural.

Decomposição funcional

Quebrar um problema grande em operações menores, nomeadas e testáveis.

Fechar pedido
validarCarrinho()
calcularFrete()
aplicarCupom()
registrarPagamento()

Cada função reduz a carga mental: o leitor não precisa entender tudo de uma vez.

A decomposição funcional é central na tradição estruturada/procedural e segue relevante em linguagens multiparadigma.

Programação procedural

Organiza o sistema como procedimentos que operam sobre dados. É muito útil para scripts, rotinas lineares, ETL simples, automações e programas com fluxo bem definido.

Pergunta típica: “Quais passos devo executar?”

$pedido = carregarPedido($id);
validarPedido($pedido);
$total = calcularTotal($pedido);
confirmarPagamento($pedido, $total);
notificarCliente($pedido);

Dados circulam entre procedimentos. A ordem de execução é parte central do projeto.

Paradigma imperativo/procedural: programas como comandos e procedimentos sobre estado.

Programação funcional

Enfatiza funções, composição, imutabilidade e transformação de valores. Sua base teórica se relaciona ao cálculo lambda, desenvolvido por Alonzo Church.

Boa metáfora: uma linha de produção onde cada estação transforma a peça sem mexer nas estações anteriores.

$nomes = array_map(
    fn($aluno) => mb_strtoupper($aluno['nome']),
    $alunos
);

$aprovados = array_filter(
    $alunos,
    fn($aluno) => $aluno['media'] >= 6
);

Rosser, “Highlights of the History of the Lambda-Calculus”; Van Roy & Haridi (2004).

Programação declarativa

Imperativo

Descrevo o passo a passo para obter o resultado.

$nomes = [];
foreach ($alunos as $a) {
  if ($a['media'] >= 6) $nomes[] = $a['nome'];
}

Declarativo

Descrevo a condição ou o resultado desejado; o motor decide a estratégia.

SELECT nome
FROM alunos
WHERE media >= 6;

Declarar é dizer “o que”; programar imperativamente é dizer “como”.

Paradigmas declarativos aparecem em SQL, linguagens lógicas, regras, queries e configurações.

Programação lógica

Na programação lógica, o programa é um conjunto de fatos e regras. A computação começa com uma consulta.

Em vez de “execute estes passos”, escrevemos relações: quem é pré-requisito de quem, quais regras permitem uma conclusão.

prerequisito(logica, poo).
prerequisito(poo, padroes).

pode_cursar(Aluno, Disciplina) :-
    aprovado(Aluno, Pre),
    prerequisito(Pre, Disciplina).

O motor lógico tenta satisfazer a consulta com base nas relações conhecidas.

Kowalski, “The Early Years of Logic Programming”; ALP Alain Colmerauer Prize: Prolog foi desenvolvido em Marseille em 1972.

Programação orientada a objetos

A POO organiza programas como uma rede de objetos com estado, comportamento e responsabilidades.

O foco muda de “quais passos executar?” para “quais entidades colaboram para resolver o problema?”

Objeto bom não é saco de dados: é uma unidade de decisão responsável.

Simula: objetos para simular o mundo

Simula nasceu no Norwegian Computing Center, associada a Ole-Johan Dahl e Kristen Nygaard, e introduziu ideias fundamentais de classes e objetos.

A motivação era modelar sistemas complexos e dinâmicos: filas, processos, entidades, eventos de simulação.

ACM A.M. Turing Award 2001: Ole-Johan Dahl e Kristen Nygaard; IEEE Milestone: Object-Oriented Programming, 1961–1967.

Smalltalk: objetos conversando por mensagens

Smalltalk, desenvolvido no ambiente do Xerox PARC, consolidou uma visão mais radical: tudo é objeto e a computação é troca de mensagens.

Alan Kay reforçou que a ideia central não era apenas “classe”, mas mensagens entre componentes autônomos.

Ações e procedimentos versus objetos e responsabilidades

Procedural

O comportamento fica espalhado em funções que recebem dados.

$total = calcularTotal($pedido);
if (podePagar($pedido)) {
  pagarPedido($pedido);
}

Orientado a objetos

O comportamento pertence ao objeto responsável.

$pedido->calcularTotal();
$pedido->pagarCom($pagamento);

POO pergunta: “quem deveria saber fazer isso?”

Design orientado a objetos: responsabilidades, encapsulamento e colaboração entre objetos.

O mesmo problema em quatro lentes

Problema: calcular o total de pedidos pagos.

Procedural

Iterar lista, somar valores, controlar variáveis.

Funcional

Filtrar pagos, mapear totais, reduzir para soma.

Declarativo

Consultar onde status = pago e agregar total.

POO

Pedido, ColeçãoDePedidos e Relatório colaboram.

O algoritmo pode ser parecido; o desenho das responsabilidades muda completamente.

Comparação didática entre estilos com base em paradigmas amplamente aceitos.

Exemplo animado em PHP: procedural → funcional → objetos

$total = 0;
foreach ($pedidos as $pedido) {
    if ($pedido['status'] === 'pago') {
        $total += $pedido['valor'];
    }
}

Procedural: fluxo explícito e variável acumuladora.

$total = array_sum(array_map(
    fn($p) => $p['valor'],
    array_filter($pedidos, fn($p) => $p['status'] === 'pago')
));

Funcional: composição de transformações.

$total = $relatorioDePedidos
    ->somentePagos()
    ->totalizar();

OO: vocabulário do domínio e responsabilidades encapsuladas.

Armadilhas comuns na transição para POO

Classe ≠ objeto

Classe é modelo; objeto é instância viva durante a execução.

Getters não são design

Encapsulamento não é só esconder atributo; é proteger invariantes.

Herança não é obrigação

Composição muitas vezes modela melhor colaboração e mudança.

O erro mais comum é escrever procedural usando classes como pastas.

Boas práticas clássicas de design orientado a objetos: encapsulamento, composição e responsabilidade única.

Miniatividade: identifique a lente

Clique no tipo de raciocínio que melhor descreve a frase.

“Quando o pagamento for confirmado, publique um evento para liberar a separação do pedido.”

Resposta esperada: orientação a eventos, possivelmente combinada com POO. O foco da frase está na reação a um acontecimento do sistema.
